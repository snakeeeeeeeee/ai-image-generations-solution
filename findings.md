# Findings

- 2026-07-27 Phase 13 starts from a clean `main` worktree at `5ee8ade`. The approved design replaces BullMQ's nondeterministic shared-queue competition with API-owned, PostgreSQL-serialized assignment to per-node queues.
- Node discovery remains automatic through Redis heartbeats. Only `WORKER_NODE_ID` and `WORKER_ADVERTISED_IP` are new per-physical-node settings; capacity continues to derive from existing worker and image-processing concurrency.
- PostgreSQL remains the assignment source of truth. BullMQ jobs must carry the assigned node and assignment version so old jobs cannot claim, complete, retry, or emit callbacks after reassignment.
- The current queue layer constructs exactly one `image-tasks` queue and workers all consume it. Worker-local recovery currently requeues every submitted/queued task and globally requeues stale processing tasks, so both behaviors must move behind assignment-aware APIs.
- Existing heartbeats already expose per-process concurrency, active work, memory, counters, hostname, PID, and container IPs. They are keyed by a random worker instance ID, which is suitable for aggregating multiple instances under the new stable node ID.
- `AsyncTaskRecord` and `TaskQueuePayload` currently contain no assignment identity. The admin UI and admin tests consume raw worker heartbeat records, so the backend response can be evolved to node aggregates while preserving a nested per-instance diagnostic list.
- Async config fixtures are constructed explicitly in multiple test files. Adding required runtime identity fields to `AsyncTaskConfig` will require updating those builders or providing carefully scoped defaults for non-worker roles.
- Base64 synchronous results were keyed only by task ID and written before PostgreSQL completion. Phase 13 must version the Redis key by assignment so a late worker cannot overwrite the current assignment's ephemeral result.
- Existing retry jobs use a distinct retry ID and worker recovery scans global queued/stale work. The new job ID will be deterministic from task ID, assignment version, and attempt; recovery can safely re-add the same job without creating a second execution or bypassing an existing delayed job.
- Phase 13 browser QA used populated two-node data at 1440px and 390px. Node ID, advertised IP, queue name, instance hostname/PID/container IP, effective capacity, and assigned task node render without page-level horizontal overflow; wide task tables retain their intentional local horizontal scroller.
- Phase 13 final verification passed 78/78 tests, the complete Vite/TypeScript production build, all three dev/prod/worker Compose config checks, and `git diff --check`. Vite emitted only the existing admin bundle size advisory.
- 2026-07-27 Phase 14: `current_tasks` is not historical and completed/retried tasks are removed from the worker runtime `Map`; however, the heartbeat and current UI expose every concurrently active task, so high-concurrency nodes can create unbounded card height.
- The approved admin redesign keeps synchronous and asynchronous workflows as separate primary views, moves low-frequency maintenance/upload actions to system tools, and caps each node task preview at three rows with an explicit remaining count.
- The existing admin API already contains all data needed for the redesign. No backend or protocol changes are required.
- The UI design-system search recommended an operations-console pattern with neutral surfaces and semantic status colors. Its default OLED-only direction is intentionally not adopted: the existing console supports both system light and dark themes, and dense tabular operations work needs equal contrast in both.
- The redesign keeps system fonts instead of adding Google Fonts so the production admin console has no new external font-loading dependency.
- Phase 14 React markup is ahead of the stylesheet: the new sidebar, workspace, overview domains/signals, and worker-node selectors have little or no CSS, while obsolete two-tab and worker-card rules still dominate. The stylesheet must explicitly supersede those old layout rules rather than only tweak colors.
- Existing table behavior is worth retaining: task tables already have sticky headers and local horizontal scrollers. Worker styling can be replaced independently with a compact node row, four-value rollup, bounded three-task area, and collapsed instance details.
